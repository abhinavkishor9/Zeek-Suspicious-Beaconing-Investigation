# Zeek-Suspicious-Beaconing-Investigation
## Overview
Network beaconing is a communication pattern in which a system repeatedly contacts another endpoint, sometimes at regular intervals. Malware may use beaconing to communicate with command-and-control (C2) infrastructure, receive instructions, or report status. However, periodic connections can also be generated by legitimate monitoring agents, software updates, health checks, and scheduled tasks.

A SOC analyst investigates potential beaconing by examining connection timestamps, destination addresses and ports, connection duration, transferred bytes, and application-layer details. Zeek's conn.log provides connection metadata, while http.log can reveal HTTP methods, URIs, response codes, and user-agent strings.

The key is to distinguish a periodic communication pattern from proof of malicious activity. Regular intervals can justify further investigation, but the analyst must consider the endpoint context, payload, destination reputation, process information, and other available evidence before classifying the activity as malicious.

This lab demonstrates how to investigate periodic network communication using Zeek and an offline packet capture. The investigation focuses on connection timing, repeated HTTP requests, connection metadata, and the limitations of interpreting beacon-like patterns without sufficient context.

The supplied PCAP contains eight HTTP connections to a local service at `127.0.0.1:8765`. The connections occur at approximately five-second intervals and contain repeated requests to `/check`. The HTTP responses and user-agent identify the traffic as a controlled lab simulation.

The objective is to learn how to identify and measure periodic communication without automatically classifying it as malicious command-and-control activity.

## Objectives

- Analyze an offline packet capture to identify recurring network communication patterns that may resemble beaconing behavior.
- Use Zeek to extract connection-level metadata, including timestamps, source and destination addresses, ports, connection durations, byte counts, and connection states.
- Identify repeated connections to a common destination and evaluate the consistency of their timing.
- Calculate connection intervals and summarize the average, minimum, and maximum intervals across the observed sessions.
- Investigate checksum-validation warnings and understand their potential impact on TCP stream reconstruction and application-protocol detection.
- Compare Zeek analysis results before and after disabling checksum validation with the `-C` option.
- Examine HTTP request and response records to identify methods, requested resources, response codes, and user-agent values.
- Correlate connection records with HTTP transactions using Zeek connection UIDs.
- Validate suspicious-looking communication patterns against packet-level evidence and available application-layer context.
- Distinguish confirmed periodic communication from suspected command-and-control activity without treating regular timing as proof of malicious intent.
- Document investigation findings, troubleshooting decisions, evidence limitations, and the final assessment using a structured network investigation approach.

## Lab scenario
You are working as a SOC Analyst investigating network traffic captured from a system that exhibits repeated connections at regular intervals. Periodic communication can be associated with malware command-and-control (C2) activity, but it can also result from legitimate application health checks, monitoring services, or scheduled tasks. Your responsibility is to investigate the available evidence and determine what the observed traffic actually establishes.

You receive an offline PCAP containing repeated TCP connections to a local service at `127.0.0.1:8765`. The initial Zeek analysis produces checksum-related warnings and does not generate the expected HTTP records. You must investigate the impact of these warnings, reprocess the capture where appropriate, and examine the resulting connection and application-layer logs.

The reprocessed data reveals eight HTTP requests to `/check`, with successful `200 OK` responses. The connection timestamps appear at approximately five-second intervals, creating a pattern suitable for periodic communication analysis.

### Investigation Tasks

- **Connection analysis:** Examine `conn.log` to identify repeated connections and review their timestamps, endpoints, ports, durations, byte counts, and connection states.
- **Interval calculation:** Calculate the time between consecutive connection starts and determine the average, minimum, and maximum intervals.
- **Troubleshooting:** Investigate the checksum warnings and compare the initial Zeek output with the results obtained using the `-C` option.
- **HTTP investigation:** Analyze `http.log` to identify request methods, URIs, response codes, and user-agent values.
- **Evidence correlation:** Correlate HTTP transactions with their corresponding connection records using Zeek connection UIDs.
- **Security assessment:** Determine whether the observed periodicity warrants further investigation and distinguish a beacon-like pattern from confirmed malicious activity.

### Expected Outcome

By completing the lab, you should be able to use Zeek to identify and measure recurring communication patterns, investigate analysis limitations, and correlate connection metadata with HTTP evidence.

Your final assessment should document the eight observed connections, their approximately five-second intervals, and the HTTP activity associated with them. The conclusion must account for the controlled test indicators in the packet contents and clearly distinguish confirmed observations from assumptions about malicious intent.

## Investigation Workflow

1. Validate the PCAP file and inspect traffic associated with TCP port `8765`.
2. Run Zeek against the capture and review its warnings and generated logs.
3. Reprocess the capture with checksum validation disabled using the `-C` option.
4. Analyze `conn.log` to identify the eight client-side connections.
5. Calculate the time between consecutive connection starts.
6. Examine `http.log` for request methods, URIs, response codes, and user-agent values.
7. Correlate the network and HTTP records using connection UIDs.
8. Assess whether the observed behavior supports a beaconing hypothesis and document the limitations.

## Key Findings

- Eight client-side TCP connections were identified to `127.0.0.1:8765`.
- The average interval between connection starts was approximately `5.003018` seconds.
- The minimum observed interval was `5.001179` seconds.
- The maximum observed interval was `5.004739` seconds.
- All eight HTTP transactions used `GET` to request `/check`.
- All eight requests received `200 OK` responses.
- The observed user-agent was `Zeek-Lab05-Controlled-Test`.
- The packet payload identified the activity as a controlled lab test.
- The initial Zeek run reported checksum-related warnings and did not reconstruct the HTTP activity as expected. Reprocessing with `-C` produced usable connection and HTTP records.

## Evidence and Limitations

- The capture contains controlled local traffic, not evidence of communication with an external C2 server.
- Periodic timing alone is not sufficient to establish malicious intent.
- The observation window is limited to eight connections.
- The `-C` option ignores checksum validation; it does not repair the PCAP or establish that all packets are valid.
- Findings are limited to the supplied capture and the Zeek records successfully generated from it.
